## 3. 本轮生成结果

新增主要接口：

- `TaskMetric`：任务级指标行。
- `compute_task_metrics(...)`：计算响应时间、拖期和加权拖期。
- `compute_metrics(...)`：计算一次实验的汇总指标。
- `compute_solver_metrics(...)`：统计求解器状态比例、耗时分位数和 MIP gap。
- `infer_task_completion_records(...)`：在未传入仿真器完成记录时，可从 `schedule_trace` 回放推断任务完成。
- `task_metrics_rows(...)` / `metrics_dataframe(...)`：提供表格输出入口，其中 DataFrame 仅在安装 pandas 时使用。

核心指标：

```text
response_time = C_j - r_j
tardiness = max(0, C_j - d_j)
weighted_tardiness = w_j * tardiness
thermal_violation_count = count(state.thermal_violation)
energy_violation_count = count(state.energy_violation)
throughput_tasks_per_slot = completed_task_count / schedule_slots
```

求解器指标包括：

- `optimal_slot_ratio`
- `feasible_slot_ratio`
- `timeout_ratio`
- `infeasible_ratio`
- `avg_solve_time_sec`
- `p50_solve_time_sec`
- `p95_solve_time_sec`
- `avg_mip_gap`
- `p95_mip_gap`
- `avg_objective_value`

### 4.4 测试项具体说明

1. `test_task_metrics_compute_response_and_weighted_tardiness`

   该测试构造一个单块任务：释放时间 `r=2`，截止期 `d=5`，权重 `w=3`，并手工构造完成记录 `C=8`。测试检查响应时间是否为 `C-r=6`，拖期是否为 `max(0, C-d)=3`，加权拖期是否为 `w*tardiness=9`。它验证的是论文实验中最常用的任务级性能指标公式没有偏移一个时隙，也没有混淆任务权重。

2. `test_summary_metrics_count_safety_violations_and_throughput`

   该测试构造 2 个任务，但只提供 1 个完成记录，表示一个任务完成、一个任务未完成。同时构造 2 条系统状态，其中第二条同时标记 `energy_violation=True` 和 `thermal_violation=True`，温度为 75 摄氏度、电量为 20 J。测试检查完成数、未完成数、热/能违反次数、最高温度和最低电量。它验证的是 `compute_metrics(...)` 能把任务完成情况和状态安全情况合并成一次实验的 summary 指标。

3. `test_solver_metrics_count_feasible_time_limit_separately`

   该测试构造 3 条求解器轨迹：`OPTIMAL`、`TIME_LIMIT` 且有可行解、`INFEASIBLE`。测试检查最优比例、超时比例、不可行比例都为 `1/3`，同时检查可行比例为 `2/3`，因为 `TIME_LIMIT` 只要 `has_feasible_solution=True` 就应计入可行解统计。它还检查平均求解耗时为 2 秒。该测试为后续 Gurobi 模块提供统计口径，避免把“超时但有可行解”和“不可行”混为一类。

4. `test_tebs_modules_are_importable`

   该测试确认 `metrics.py` 可被自动导入。对第9轮来说，它还间接验证 `metrics_dataframe(...)` 没有在模块导入时强制依赖 pandas，而是只有调用 DataFrame 输出接口时才检查 pandas 是否安装。
