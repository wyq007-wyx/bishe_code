# 任务进度推进机制说明

本文档整理当前 TEBS 调度仿真代码中“任务进度如何推进”的统一表示，并说明各类调度方案在该表示下的差异。

相关代码：

- `tebs_scheduler/src/tebs/simulator.py`
- `tebs_scheduler/src/tebs/scheduler_base.py`
- `tebs_scheduler/src/tebs/baseline_dvfs.py`
- `tebs_scheduler/src/tebs/baseline_intermittent.py`
- `tebs_scheduler/src/tebs/models.py`

## 1. 基本对象

### 1.1 任务块执行时长

每个任务由一个或多个 `TaskBlock` 组成。任务块在不同核心上的执行时长存储在：

```python
TaskBlock.duration_by_core
```

其含义为：

```text
D_{j,b,c} = 任务 j 的任务块 b 在核心 c 上，以默认/高频等效方式完成所需的 slot 数
```

其中：

- `j`：任务 ID
- `b`：任务块 ID
- `c`：核心 ID
- `D_{j,b,c}`：执行时长，单位为 slot

例如：

```python
duration_by_core = {
    "hp_0": 4,
    "lp_0": 7,
}
```

表示该任务块在 `hp_0` 上需要 4 个 slot，在 `lp_0` 上需要 7 个 slot。

### 1.2 剩余工作量

仿真器内部为每个任务块维护：

```python
remaining_slots
```

其含义为：

```text
R_{j,b}(t) = 时隙 t 开始时，任务 j 的任务块 b 剩余的高频等效工作量
```

任务块第一次被调度到某个核心上执行时，仿真器初始化：

```text
R_{j,b}(t) = D_{j,b,c}
```

对应代码在 `simulator.py`：

```python
if block_progress.remaining_slots is None:
    block_progress.remaining_slots = float(block.duration_by_core[decision.core_id])
```

## 2. 统一进度更新公式

仿真器每个时隙读取调度器返回的 `ScheduleDecision`。若某个核心在该时隙执行任务块，则按如下公式推进任务进度：

```text
R_{j,b}(t+1) = R_{j,b}(t) - g(t)
```

其中：

```text
g(t) = 当前时隙推进的高频等效 slot 数
```

在代码中，`g(t)` 对应：

```python
progress_slots
```

如果调度器没有显式提供运行效果，则默认：

```text
g(t) = 1.0
```

对应代码：

```python
runtime_effect = runtime_effect_by_core.get(decision.core_id)
progress_slots = runtime_effect.progress_slots if runtime_effect is not None else 1.0
block_progress.remaining_slots -= progress_slots
```

任务块完成条件：

```text
R_{j,b}(t+1) <= 0
```

对应代码：

```python
if block_progress.remaining_slots <= 0:
    block_progress.completed = True
```

当一个任务的所有任务块都完成时，仿真器生成 `TaskCompletionRecord`：

```text
C_j = current_time + 1
```

其中 `C_j` 是任务完成时间。

## 3. 调度动作与运行效果

第10轮后，`SchedulerResult` 支持可选运行效果：

```python
runtime_effect_by_core: dict[str, DecisionRuntimeEffect] | None
```

`DecisionRuntimeEffect` 包含：

```python
progress_slots: float = 1.0
compute_power_w: float | None = None
```

含义：

- `progress_slots`：当前时隙推进多少高频等效工作量。
- `compute_power_w`：当前调度动作实际产生的计算功耗。

如果某个调度器不提供 `runtime_effect_by_core`，仿真器采用默认行为：

```text
progress_slots = 1.0
compute_power_w = TaskBlock.power_by_core[core_id]
```

这保证了第1-9轮已有模块和后续普通调度器不需要额外修改。

## 4. 普通块级调度方案

适用方案：

- `SafeIdleScheduler`
- 后续 `FCFS-Gurobi`
- 后续 `RHC-MILP-Gurobi`
- 后续 `TCN-Scheduler`
- 后续 `Hybrid-Gurobi-TCN`
- 其他不使用 DVFS 或暂停机制的普通调度器

### 4.1 执行时

如果某时隙核心 `c` 执行任务块 `(j, b)`：

```text
g(t) = 1.0
R_{j,b}(t+1) = R_{j,b}(t) - 1.0
P_com(t) += P_{j,b,c}
```

其中：

```text
P_{j,b,c} = TaskBlock.power_by_core[c]
```

### 4.2 空闲时

如果核心 idle：

```text
g(t) = 0
P_com(t) 不增加
R_{j,b}(t+1) = R_{j,b}(t)
```

空闲动作不会进入任务块进度扣减逻辑。

### 4.3 举例

任务块在 `hp_0` 上执行时长为 4 slot：

```text
R(0) = 4
第 0 个时隙执行：R(1) = 4 - 1 = 3
第 1 个时隙执行：R(2) = 3 - 1 = 2
第 2 个时隙执行：R(3) = 2 - 1 = 1
第 3 个时隙执行：R(4) = 1 - 1 = 0，任务块完成
```

如果该任务只有一个任务块，则任务完成时间为：

```text
C_j = 4
```

## 5. FCFS-DVFS 方案

对应模块：

```text
tebs_scheduler/src/tebs/baseline_dvfs.py
```

### 5.1 队列规则

`FcfsDvfsScheduler` 固定使用 FCFS 队列：

```text
queue = sort(tasks, key=(release_time, task_id))
```

调度器只尝试执行未完成的队首任务，不跳过队首任务。

### 5.2 频率档位

默认三档频率如下：

| 档位 | `frequency_scale` | `voltage_scale` | 含义 |
|---|---:|---:|---|
| `high` | 1.0 | 1.0 | 高频，按普通速度推进 |
| `medium` | 0.7 | 0.85 | 中频，推进速度降低 |
| `low` | 0.5 | 0.75 | 低频，推进速度最低 |

### 5.3 频率选择规则

```text
if T(t) >= T_crit or E(t) <= E_crit:
    q(t) = low
elif T(t) >= T_warn or E(t) <= E_warn:
    q(t) = medium
else:
    q(t) = high
```

含义：

- 温度过高或电量过低时，选择低频。
- 温度或电量接近风险区间时，选择中频。
- 热-电状态安全时，选择高频。

### 5.4 进度推进公式

DVFS 下，任务进度不再固定推进 1 个 slot，而是按频率比例推进：

```text
g_q = f_q / f_H
R_{j,b}(t+1) = R_{j,b}(t) - g_q
```

当前代码中：

```text
high:   g = 1.0
medium: g = 0.7
low:    g = 0.5
```

例如任务块原始执行时长为 4 slot：

```text
低频运行 1 个时隙：
R(1) = 4 - 0.5 = 3.5

低频连续运行 8 个时隙：
R(8) = 4 - 8 * 0.5 = 0，任务块完成
```

因此 DVFS 会降低瞬时功耗，但任务完成时间会变长。

### 5.5 功耗推进公式

DVFS 功耗按频率和电压缩放：

```text
P_dvfs = P_high * (V_q / V_H)^2 * (f_q / f_H)
```

当前代码中：

```python
power_scale = voltage_scale * voltage_scale * frequency_scale
```

举例：

```text
P_high = 10 W
low: voltage_scale = 0.75, frequency_scale = 0.5

P_low = 10 * 0.75^2 * 0.5
      = 2.8125 W
```

### 5.6 代码实现方式

`FcfsDvfsScheduler` 返回 `ScheduleDecision` 时，会附带：

```python
DecisionRuntimeEffect(
    progress_slots=frequency_scale,
    compute_power_w=scaled_power_w(...)
)
```

仿真器读取该运行效果后：

```text
剩余工作量按 frequency_scale 扣减
计算功耗按 compute_power_w 计入 P_com
```

## 6. FCFS-Intermittent 方案

对应模块：

```text
tebs_scheduler/src/tebs/baseline_intermittent.py
```

### 6.1 队列规则

`FcfsIntermittentScheduler` 同样固定使用 FCFS 队列：

```text
queue = sort(tasks, key=(release_time, task_id))
```

恢复后继续原队首任务，不跳到后续任务。

### 6.2 暂停规则

```text
if T(t) >= T_pause or E(t) <= E_pause:
    pause all compute cores
```

进入暂停状态后：

```text
all decisions = idle
P_com(t) = 0
g(t) = 0
R_{j,b}(t+1) = R_{j,b}(t)
```

即：

- 所有核心空闲；
- 不产生计算功耗；
- 不推进任何任务进度；
- 只保留系统基础功耗 `P_base`。

### 6.3 恢复规则

```text
if T(t) <= T_resume and E(t) >= E_resume:
    resume compute
```

恢复后继续执行暂停前尚未完成的 FCFS 队首任务块。

当前阈值使用滞回设计：

```text
T_resume <= T_pause
E_resume >= E_pause
```

这样可以避免系统状态在阈值附近频繁暂停/恢复。

### 6.4 正常运行时的进度

未暂停时，间歇计算基线使用普通进度推进：

```text
g(t) = 1.0
R_{j,b}(t+1) = R_{j,b}(t) - 1.0
P_com(t) += P_{j,b,c}
```

### 6.5 暂停举例

任务块原始执行时长为 3 slot：

```text
R(0) = 3

第 0 个时隙正常执行：
R(1) = 3 - 1 = 2

第 1 个时隙触发暂停：
R(2) = 2
P_com = 0

第 2 个时隙仍暂停：
R(3) = 2
P_com = 0

第 3 个时隙满足恢复阈值，继续执行：
R(4) = 2 - 1 = 1
```

这体现了间歇计算的核心特征：约束风险高时牺牲吞吐量以换取安全。

## 7. 后续 Gurobi / TCN 方案的接入建议

后续第12轮以后会实现 `FCFS-Gurobi`、`RHC-MILP-Gurobi`、`TCN-Scheduler` 和 `Hybrid-Gurobi-TCN`。这些方法可以复用当前统一进度语义。

### 7.1 不使用 DVFS 时

如果方法只决定“哪个任务块在哪个核心执行”，不改变频率，则无需传 `runtime_effect_by_core`：

```text
g(t) = 1.0
P_com(t) = TaskBlock.power_by_core[core_id]
```

### 7.2 使用频率或速度缩放时

如果后续方法也要控制频率、速度或近似执行比例，则应显式传：

```python
DecisionRuntimeEffect(
    progress_slots=progress_scale,
    compute_power_w=effective_power_w,
)
```

这样仿真器仍使用同一套推进公式：

```text
R_{j,b}(t+1) = R_{j,b}(t) - progress_slots
```

### 7.3 MILP 建模中的对应关系

若用离散二元变量表示任务块是否在时隙 `t` 被核心 `c` 执行，可写成：

```text
x_{j,b,c,t} in {0, 1}
```

普通频率下的完成约束：

```text
sum_{c,t} x_{j,b,c,t} >= D_{j,b,c}
```

若引入 DVFS 档位 `q`：

```text
x_{j,b,c,q,t} in {0, 1}
sum_{c,q,t} g_q * x_{j,b,c,q,t} >= D_{j,b,c}
```

其中：

```text
g_q = f_q / f_H
```

## 8. 指标统计注意事项

### 8.1 优先使用仿真器完成记录

对于普通调度，`metrics.py` 可以从 `schedule_trace` 回放推断任务完成时间。

但对于 DVFS 方案，任务进度依赖 `runtime_effect_by_core.progress_slots`。当前 `ScheduleTrace` 只记录了 `ScheduleDecision`，没有保存每个决策对应的 `progress_slots`。因此 DVFS 实验统计应优先使用仿真器输出的：

```python
SimulationResult.task_completion_records
```

然后调用：

```python
compute_metrics(
    tasks=tasks,
    schedule_trace=result.schedule_trace,
    state_trace=result.state_trace,
    completion_records=result.task_completion_records,
)
```

这样可以避免把低频运行错误地回放成每时隙推进 1 个 slot。

### 8.2 间歇计算的统计

间歇计算暂停期间所有核心 idle，因此 `schedule_trace` 中没有非 idle 动作，回放时自然不会推进任务进度。

不过，为了保持所有方案统计口径一致，仍建议统一使用仿真器输出的 `task_completion_records`。

## 9. 总结

当前代码中任务进度推进可以统一理解为：

```text
剩余工作量 = 剩余工作量 - 当前时隙推进量
```

不同方案的区别只在于“当前时隙推进量”和“当前时隙计算功耗”：

| 方案 | 执行时推进量 `g(t)` | 暂停/空闲时推进量 | 计算功耗 |
|---|---:|---:|---|
| 普通调度 / Gurobi / TCN | 1.0 | 0 | `TaskBlock.power_by_core[c]` |
| FCFS-DVFS high | 1.0 | 0 | 原始功耗 |
| FCFS-DVFS medium | 0.7 | 0 | 按 `0.85^2 * 0.7` 缩放 |
| FCFS-DVFS low | 0.5 | 0 | 按 `0.75^2 * 0.5` 缩放 |
| FCFS-Intermittent 正常运行 | 1.0 | 0 | 原始功耗 |
| FCFS-Intermittent 暂停 | 0 | 0 | 0 |

这套表示能同时覆盖当前第1-11轮已实现代码，也能支撑后续 Gurobi、TCN 和混合调度器继续扩展。
