## 3. 本轮生成结果

新增主要接口：

- `TaskCompletionRecord`：任务完成记录，包含完成时间和已完成块 ID。
- `SimulationResult`：完整仿真输出。
- `initial_state_from_config(...)`：从配置生成初始 `SystemState`。
- `run_simulation(...)`：统一仿真入口。

仿真循环每个时隙执行：

1. 从环境序列读取当前 `P_harv`、`P_base` 和环境温度。
2. 调用 `scheduler.decide(...)` 获取 `SchedulerResult`。
3. 校验调度动作中的核心、任务和任务块引用。
4. 根据动作推进任务块剩余执行时长。
5. 汇总当前时隙 `P_com`。
6. 调用 `update_energy(...)` 更新电量。
7. 调用 `update_temperature(...)` 更新温度。
8. 写入 `schedule_trace`、`state_trace`、`task_completion_records` 和 `solver_trace`。

### 4.4 测试项具体说明

1. `test_idle_scheduler_runs_complete_simulation_cycle`：空闲调度器闭环

   该测试构造 2 个异构核心、6 个环境时隙和一个初始系统状态，然后使用 `SafeIdleScheduler` 运行 `run_simulation(...)`。首先检查 `schedule_trace` 和 `state_trace` 都有 6 条记录，确认主循环没有提前停止或漏写状态。由于任务集为空，测试还确认 `task_completion_records` 长度为 0。它验证的是即使没有任务，仿真器也能完整执行环境读取、调度调用、能量更新和热更新流程。

2. `test_idle_scheduler_runs_complete_simulation_cycle`：每核心动作唯一

   同一个测试进一步检查每条 `ScheduleTrace` 中的动作数量是否等于核心数量，并检查同一时隙内核心 ID 是否唯一。它验证的是仿真器接收到调度器输出后，能保持“每个核心每个时隙最多一个动作”的基本调度约束。

3. `test_idle_scheduler_runs_complete_simulation_cycle`：系统状态更新

   该测试比较第一个输出状态的 `energy_joule` 和初始电量，预期二者不同。因为即使所有核心 idle，系统仍然有基础功耗，也可能有太阳能输入，所以电量必须发生更新。它验证的是仿真主循环没有只记录初始状态，而是在每个时隙真实调用了能量模型；同时热模型也在同一流程中被调用并写入状态轨迹。

4. `test_idle_scheduler_runs_complete_simulation_cycle`：空任务完成记录

   该测试输入空任务列表，预期仿真结果中没有任务完成记录。它验证的是完成记录只由实际任务块执行完成触发，仿真器不会在无任务场景下产生伪完成项。

5. `test_tebs_modules_are_importable`

   该测试确认 `simulator.py` 可被自动导入。对第8轮来说，它保证仿真器模块不会在 import 时自动启动仿真、加载任务集或写输出文件，后续实验运行器可以安全导入该模块。
