### 3.2 `models.py` 实现内容

实现了第1轮要求的共享数据结构：

- `Task`
- `TaskBlock`
- `Core`
- `SystemState`
- `ScheduleDecision`
- `ScheduleTrace`
- `SolverTrace`

并将 `ScheduleTrace` 的字段统一为 `decisions: list[ScheduleDecision]`。

### 3.3 关键校验逻辑

- 任务块核心映射校验：
  - `duration_by_core` 与 `power_by_core` 核心集合必须一致。
  - 在 `Task.core_ids` 给定时，每个任务块核心集合必须是其子集（支持多阶段差异核心适配）。
  - 可选开启 `require_uniform_block_core_ids=True`，要求任务内所有块使用一致核心集合。
- 时间合法性校验：
  - `release_time <= deadline`。
- 前驱顺序校验：
  - `predecessor_block_id < block_id`。
  - 且必须指向任务内已出现的更早块。
- 调度动作表达校验：
  - `ScheduleDecision.idle(...)` 表示核心空闲。
  - `ScheduleDecision.run(...)` 表示核心执行任务（支持任务级和任务块级两种粒度）。

### 3.4 核心代码逻辑说明

`models.py` 采用“构造即校验”的实现方式：对象一旦创建成功，就满足后续模块可直接依赖的基础约束。

核心逻辑如下：

1. `TaskBlock`（任务块原子单元）
   - 校验 `release_time <= deadline`；
   - 校验 `duration_by_core` 与 `power_by_core` 的核心集合一致；
   - 校验 `predecessor_block_id < block_id`，避免同层或逆序前驱。
2. `Task`（任务聚合单元）
   - 要求至少一个 `TaskBlock`；
   - 校验所有块 `task_id` 一致、`block_id` 唯一；
   - 校验前驱必须指向已出现的更早块，保证顺序合法。
   - 不强制 `Task.deadline` 等于最后一个任务块的 `deadline`；
   - 提供 `Task.single_block(...)`，用于把不划分任务块的对比方案统一表示为单块任务。
3. `Core`（异构核心建模）
   - `core_type` 统一为 `high_performance`/`low_power`；
   - 新增 `build_cores_from_type_counts(...)`，可按两类核心数量生成核心列表。
4. `ScheduleDecision`（统一调度动作）
   - 空闲动作：`is_idle=True` 且不允许携带任务字段；
   - 执行动作：`is_idle=False` 且必须携带 `task_id`，`block_id` 可选：
     - `block_id=None`：任务级决策（规则基线）
     - `block_id=int`：任务块级决策（块级方法）
5. `ScheduleTrace`（时隙动作记录）
   - 要求 `decision.time_slot` 与轨迹 `time_slot` 一致；
   - 限制同一时隙每个核心最多一条决策，避免冲突分配。
6. `SystemState` / `SolverTrace`
   - `SystemState` 保证状态字段合法（例如电量非负）；
   - `SolverTrace` 统一承载求解状态、耗时、`MIPGap` 等统计输入。

### 3.5 架构说明

第一轮采用“领域模型先行”的架构策略，把共享数据契约固定下来，再推进后续模块。

1. 工程分层
   - `tebs_scheduler/src/tebs/models.py`：领域数据模型与约束边界；
   - `tebs_scheduler/tests/test_models.py`：模型契约测试；
   - `tebs_scheduler/tests/test_imports.py`：包导入与工程骨架有效性测试。
2. 依赖方向
   - 后续模块（`task_factory`、`environment`、`scheduler`、`simulator`、`metrics`）只依赖 `models.py`，不反向依赖。
3. 架构价值
   - 在第一轮提前统一字段命名和合法性规则；
   - 降低后续轮次接口漂移和跨模块返工概率；
   - 让仿真闭环和 Gurobi/学习模块能共享同一份数据语义。

### 4.4 测试项具体说明

1. `test_tebs_modules_are_importable`

   该测试遍历 `tebs` 包下所有模块并逐个导入。对第1轮来说，它确认工程骨架、`src` 布局、`pyproject.toml` 的 `pythonpath` 配置以及 `tebs.__init__` 导出均可正常工作。这个测试能尽早发现包名错误、路径配置错误或模块导入阶段副作用。

2. `test_task_block_core_maps_must_match`

   该测试构造一个任务块，其中 `duration_by_core` 包含 `hp_0` 和 `lp_0`，但 `power_by_core` 只包含 `hp_0`。预期构造时直接抛出错误。它验证的是同一个任务块在任一核心上只要有执行时长，就必须同时有对应功耗，避免后续调度器能选中一个“有时长但无功耗”或“有功耗但无时长”的非法动作。

3. `test_release_time_must_not_exceed_deadline`

   该测试分别构造非法任务块和非法任务，让 `release_time` 大于 `deadline`。预期二者都会抛出 `ValueError`。它验证的是时间窗不倒置这一基础约束在任务块级和任务级都成立，防止后续任务工厂或调度器接收到不可调度的时间窗口。

4. `test_predecessor_order_must_be_legal`

   该测试覆盖两类非法前驱：任务块自己的 `predecessor_block_id` 等于自身 `block_id`，以及任务内块从 `block_id=1` 开始但指向不存在的 `block_id=0`。测试也构造了一个合法的 `0 -> 1` 前驱链。它验证的是多阶段任务必须形成可拓扑展开的顺序链，避免仿真器或 MILP 约束中出现环依赖或悬空依赖。

5. `test_task_block_core_set_is_subset_of_task_core_ids`

   该测试先构造一个合法任务：任务声明可用核心为 `hp_0, lp_0`，两个任务块分别只使用其中一个核心。随后构造非法任务块，让它使用 `hp_2`。预期非法情况报错。它验证的是任务级 `core_ids` 可以作为核心全集约束，块级核心映射可以是全集子集，但不能越界引用未知核心。

6. `test_task_can_optionally_require_uniform_block_core_set`

   该测试验证 `require_uniform_block_core_ids` 的两种语义。默认值为 `False` 时，多阶段任务可以让不同阶段使用不同核心集合；设置为 `True` 时，如果不同块核心集合不一致，则构造任务时报错。它为后续任务工厂的“所有块覆盖同一核心集合”和更灵活的多阶段异构适配都保留了接口。

7. `test_task_single_block_constructor_for_task_level_baselines`

   该测试调用 `Task.single_block(...)` 构造任务级基线常用的单块任务，并检查任务 ID、释放时间、截止期、权重和块字段是否一致。它验证的是不显式划分任务块的 FCFS 类方法也能统一转换为 `Task -> TaskBlock` 结构，减少后续仿真器的分支逻辑。

8. `test_task_deadline_does_not_need_to_equal_last_block_deadline`

   该测试构造一个任务级截止期为 20、最后任务块截止期为 12 的任务，并确认两者可以不同。它验证的是任务级截止期表示整体时效目标，块级截止期表示局部约束，两者不被模型层强行绑定，便于后续更精细的约束建模。

9. `test_system_state_fields_and_temperature_validation`

   该测试构造合法系统状态、低电量但非负的系统状态，以及负电量、NaN/Inf 温度、低于绝对零度温度等非法状态。它验证的是 `SystemState` 只负责物理合法性：电量不能为负，温度必须有限且不低于绝对零度；安全电量下限 `E_min` 留给第5轮能量模型用 `energy_violation` 记录。

10. `test_build_cores_from_type_counts`

    该测试按 `high_performance_count=2`、`low_power_count=2` 生成核心，检查核心 ID 顺序和核心类型是否符合约定，并验证负数核心数量会报错。它验证的是后续配置模块可以直接通过两类核心数量批量生成异构核心集合。

11. `test_schedule_decision_supports_run_and_idle`

    该测试分别构造 idle 决策、任务块级 run 决策和任务级 run 决策，并检查字段语义。它还构造缺少 `task_id` 的非 idle 决策和负数 `block_id` 决策，确认会报错。它验证的是第1轮把 `ScheduleAction` 与 `ScheduleDecision` 统一后，仍能表达空闲、任务级调度和块级调度三种情况。
