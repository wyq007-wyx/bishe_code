### 3.2 `rhc_milp_gurobi.py` 实现内容

新增主要对象与接口：

- `RhcObjectiveWeights`：目标函数权重，包含 `alpha`、`beta`、`mu`。
- `RhcWindowAssignment`：记录滚动窗口计划中的时隙、核心、任务块、时长和功耗。
- `RhcMilpGurobiScheduler`：滚动时域 MILP 调度器。
- `RhcMilpGurobiError`：Gurobi 求解失败且禁用 fallback 时的清晰错误。

滚动时域流程：

```text
1. 在当前时隙 t0 读取系统电量、温度、任务集合、核心集合和环境窗口。
2. 选取窗口 [t0, t0 + H - 1] 内已释放或将释放、且前驱已完成的候选任务块。
3. 建立 slot-level MILP。
4. 求解窗口计划。
5. 只执行当前时隙 t0 的动作。
6. 记录 SolverTrace 与 last_window_plan。
7. 下一时隙重新观测状态并滚动求解。
```

当前 MILP 主要约束：

```text
每个核心每个时隙最多执行一个任务块
每个任务块每个时隙最多占用一个核心
任务 release time 前不能调度
前驱未完成的后继块不进入候选集合
窗口内至少服务一个可行任务块
累计能量不低于 E_min
每个时隙计算热量不超过热预算
x[j, c, t] in {0, 1}
```

目标函数采用第7节主方法目标的轻量实现：

```text
min alpha * weighted_response_proxy
  + beta  * weighted_tardiness_proxy
  - mu    * served_work_reward
  + small_receding_penalty
```

其中响应时间和拖期使用窗口内分配时隙加执行时长构造代理值，`served_work_reward` 鼓励优先服务高权重任务。由于现有仿真器是逐 slot 推进，本轮实现与仿真器保持一致：MILP 输出窗口计划，但每轮只提交当前时隙动作。

### 3.3 无 Gurobi 环境行为

模块导入不依赖 Gurobi。调度器默认 `fallback_to_idle_on_error=True`，当 `gurobipy` 不存在或 license 不可用时，会返回安全 idle 并记录 `GUROBI_UNAVAILABLE` 或 `UNKNOWN` 状态。测试中真正求解的用例会在无 Gurobi 时自动 skip。

### 4.4 测试项具体说明

1. `test_rhc_milp_solves_small_case_with_core_capacity`

   该测试构造两个单块任务和两个异构核心。MILP 允许任务重排和核心选择，但必须满足每个核心在当前时隙最多一个动作。测试检查当前非 idle 决策的核心 ID 不重复，并检查求解 trace 有可行解、窗口计划非空。当前环境无可用 Gurobi，因此该求解型测试 skip。

2. `test_rhc_milp_does_not_schedule_successor_before_predecessor`

   该测试构造一个两块任务，block 1 的 `predecessor_block_id=0`。由于 block 0 尚未完成，block 1 不应进入候选集合，也不应出现在窗口计划或当前动作中。它验证的是任务内部顺序约束。

3. `test_rhc_milp_respects_release_time_before_current_slot`

   该测试构造一个 release time 为 2 的任务，并在时隙 0 调用调度器。预期当前动作全 idle；如果窗口计划存在，也只能从时隙 2 或之后开始。它验证的是释放时间约束不仅影响当前动作，也影响窗口计划。

4. `test_rhc_milp_idles_when_energy_constraint_is_infeasible`

   该测试把 `E_min` 设为接近当前电量，并设置无太阳能输入，使任何计算功耗都会触碰能量下限。预期 MILP 无可行解，调度器返回安全 idle，并在 `SolverTrace` 中记录 `has_feasible_solution=False`。它验证的是能量安全约束进入求解模型，而不是仅在仿真器后验统计。

5. `test_tebs_modules_are_importable`

   该测试确认主方法模块能在没有 Gurobi 的环境中导入，保证后续规则基线和非 Gurobi 实验不会被可选依赖阻断。
