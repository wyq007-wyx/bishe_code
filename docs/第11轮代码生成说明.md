### 3.2 `baseline_intermittent.py` 实现内容

新增主要对象与接口：

- `IntermittentThresholds`：暂停/恢复阈值，包含温度和电量滞回区间。
- `IntermittentPauseState`：记录当前是否暂停以及累计暂停次数。
- `should_pause(...)`：判断当前系统状态是否应暂停计算。
- `should_resume(...)`：判断暂停状态下是否可恢复计算。
- `FcfsIntermittentScheduler`：固定 FCFS 队列的暂停-恢复调度器。

暂停规则：

```text
if T(t) >= T_pause or E(t) <= E_pause:
    pause all compute cores
```

恢复规则：

```text
if T(t) <= T_resume and E(t) >= E_resume:
    resume previous task
```

暂停期间：

```text
all decisions are idle
P_com(t) = 0
task progress does not increase
```

### 3.3 与 FCFS 队列的关系

`FcfsIntermittentScheduler` 采用固定 FCFS 队列：

1. 任务按 `(release_time, task_id)` 排序。
2. 未完成的队首任务优先。
3. 如果队首任务未释放或前驱块未完成，则所有核心 idle。
4. 暂停恢复后继续原队首任务，不跳到后续任务。

### 4.4 测试项具体说明

1. `test_pause_threshold_makes_all_cores_idle`

   该测试构造一个高温系统状态：温度为 65 摄氏度，超过暂停阈值 `T_pause=60`。调用调度器后，测试检查 `should_pause(...)` 是否为 `True`，所有返回决策是否都是 idle，以及调度器内部 `pause_state.is_paused` 是否被置为 `True`。它验证的是热约束风险出现时，间歇计算基线会立刻停止所有计算核心。

2. `test_pause_period_has_zero_compute_power_and_no_task_progress`

   该测试先在安全状态下运行一次队首任务 `T0`，记录它的剩余工作量；随后把系统切到高温暂停状态，再调用一次调度器。测试检查暂停时所有核心 idle，`last_compute_power_w=0`，并确认 `T0` 的剩余工作量没有变化。它验证的是暂停期间只保留基础功耗，不产生计算功耗，也不会推进任务进度。

3. `test_resume_threshold_continues_previous_fcfs_task`

   该测试构造两个任务 `T0` 和 `T1`。调度器先在安全状态下执行 `T0`，随后因高温暂停，再在温度回落到 45 摄氏度且电量充足时恢复。测试检查 `should_resume(...)` 是否为 `True`，恢复后的非 idle 决策仍指向 `T0`，且暂停状态解除。它验证的是间歇计算恢复后继续原队首任务，不会因为暂停而跳到后续任务。

4. `test_fcfs_intermittent_does_not_skip_queue_head_task`

   该测试构造两个同时可运行任务 `T0` 和 `T1`，并给系统安全状态。调度器应选择 FCFS 队首 `T0`。它验证的是间歇计算基线同样没有任务重排能力，只是在固定队列上执行暂停/恢复策略。

5. `test_tebs_modules_are_importable`

   该测试确认 `baseline_intermittent.py` 可以被自动导入，并确认 `__init__.py` 中新增导出不会造成循环导入或导入阶段异常。
