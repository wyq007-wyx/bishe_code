### 3.2 `config.py` 实现内容

实现了第2轮要求的配置对象与加载逻辑：

- `SimulationConfig`
- `GurobiConfig`
- `ThermalConfig`
- `EnergyConfig`
- `ConfigBundle`
- `load_config(...)` / `load_config_from_mapping(...)`
- `default_config_path()`

#### 3.2.1 配置对象职责

- `SimulationConfig`：保存仿真层参数，包括 `delta_t_seconds`、`horizon_slots`、`simulation_slots`、异构核心数量、日照/阴影周期和能量单位。
- `GurobiConfig`：保存求解器参数，包括 `gurobi_time_limit`、`gurobi_mip_gap`、`gurobi_threads` 和 `gurobi_verbose`。
- `ThermalConfig`：保存热模型参数，包括初始温度、温度上限、环境温度、等效热容和冷却系数。
- `EnergyConfig`：保存能量模型参数，包括电池容量上限、最低安全电量、初始电量、基础功耗、太阳能峰值采集功率和轨道相位功率模型。
- `ConfigBundle`：把上述四类配置聚合在一起，作为后续模块统一读取的配置入口。

#### 3.2.2 配置加载流程

`load_config(config_path=None)` 是对外主入口：

1. 如果调用方未传入路径，则通过 `default_config_path()` 定位到 `tebs_scheduler/configs/default_sim.yaml`。
2. `_load_yaml_mapping(...)` 负责读取 YAML 文件，并检查根节点是否为 mapping。
3. `load_config_from_mapping(...)` 将 YAML 字典拆分为 `simulation`、`gurobi`、`thermal`、`energy` 四个 section。
4. 每个 section 缺失时使用空字典处理，每个字段缺失时回退到代码中的默认值。
5. 最终构造 `ConfigBundle`，后续模块只需要消费 `cfg.simulation`、`cfg.energy`、`cfg.thermal`、`cfg.gurobi`。

#### 3.2.3 字段读取与校验逻辑

配置模块使用一组私有读取函数保证输入类型清晰：

- `_read_int(...)`：读取整数，禁止把 `bool` 当作整数使用。
- `_read_float(...)`：读取数值，允许 `int` 或 `float`，但禁止 `bool`。
- `_read_str(...)`：读取非空字符串。
- `_read_bool(...)`：读取布尔值。

构造 dataclass 后还会执行范围校验：

- `delta_t_seconds`、`horizon_slots`、`simulation_slots` 必须大于 0。
- 高性能核数量和低功耗核数量必须非负，且总核心数必须大于 0。
- 日照时长和阴影时长必须非负，二者之和必须大于 0。
- `energy_unit` 必须为 `J`，确保内部能量计算单位统一。
- `gurobi_time_limit` 必须大于 0，`gurobi_mip_gap` 和线程数必须非负。
- `e_min_j < e_max_j`，且 `initial_energy_j` 必须落在 `[e_min_j, e_max_j]` 内。
- `solar_power_profile` 必须为 `constant` 或 `half_sine_orbit`。
- `solar_power_min_ratio` 必须落在 `[0, 1]` 内。
- `thermal_capacity_j_per_c` 必须大于 0，`cooling_coeff` 必须非负，`t_max_celsius` 必须高于环境温度。

#### 3.2.4 核心数量兼容逻辑

当前代码将核心数量拆成了两类：

- `high_performance_core_count`
- `low_power_core_count`

这是为了贴合实验方案中“2 个高性能核 + 2 个低功耗核”的异构多核设定。为了兼容旧配置，`_resolve_core_type_counts(...)` 仍支持旧字段 `core_count`：

- 若 YAML 中显式给出 `high_performance_core_count` 或 `low_power_core_count`，则优先使用新版字段。
- 若 YAML 中只给出旧版 `core_count`，则自动拆分为两类核心：高性能核为 `core_count // 2`，低功耗核为剩余数量。
- `SimulationConfig.core_count` 作为只读属性保留，返回两类核心数量之和，方便旧代码继续访问总核心数。

#### 3.2.5 异常设计

所有配置相关错误统一抛出 `ConfigError`，包括：

- 配置文件不存在；
- YAML 根节点不是字典结构；
- section 类型不是 mapping；
- 字段类型错误；
- 字段数值范围非法；
- 能量单位不是 `J`。

这种设计让后续 `task_factory.py`、`environment.py`、`energy_model.py`、`thermal_model.py` 和 Gurobi 相关模块可以在配置加载阶段尽早失败，避免错误延迟到仿真运行中才暴露。

### 3.3 默认参数落地

`configs/default_sim.yaml` 已固化关键默认参数：

- `simulation.delta_t_seconds = 60`
- `simulation.horizon_slots = 12`
- `simulation.simulation_slots = 194`
- `simulation.high_performance_core_count = 2`
- `simulation.low_power_core_count = 2`
- `simulation.sunlight_duration_slots = 61`
- `simulation.eclipse_duration_slots = 36`
- `gurobi.gurobi_time_limit = 5.0`
- `gurobi.gurobi_mip_gap = 0.01`
- `simulation.energy_unit = J`

并补充了后续模块直接可复用的初值：

- 能量边界与初始电量（`e_max_j = 144000.0` / `e_min_j = 115200.0` / `initial_energy_j = 129600.0`）
- 温度初值与上限（`initial_temperature_celsius = 25.0` / `t_max_celsius = 70.0`）
- 环境相关缺省功率（`default_base_power_w = 3.6` / `default_max_solar_power_w = 14.0`，其中太阳能功率为峰值）
- 太阳能轨道变化模型（`solar_power_profile = half_sine_orbit` / `solar_power_min_ratio = 0.0`）
- 近地轨道日照/阴影周期（约 `60 min 52 s` 日照、`35 min 38 s` 阴影，按 60 s 时隙取整为 `61/36 slots`）
- 详细依据见 `docs/默认参数设置依据.md`

### 3.4 第2轮扩展配置文件

为后续轮次预置：

- `configs/scenarios.yaml`：S1/S2/S3 场景模板
- `configs/gurobi.yaml`：`fast/balanced/quality` 求解参数模板

`configs/scenarios.yaml` 中三个场景的用途如下：

- `S1_light`：轻负载场景，任务数量较少，高功耗任务比例较低，适合后续基础冒烟测试。
- `S2_mixed`：混合负载默认对比场景，作为常规实验配置模板。
- `S3_stress`：高压力场景，高功耗任务比例更高，用于验证调度方法在资源紧张条件下的表现。

`configs/gurobi.yaml` 中三个 profile 的用途如下：

- `fast`：更短的 `TimeLimit` 和更宽松的 `MIPGap`，用于快速验证。
- `balanced`：与默认实验参数一致，用于主要对比实验。
- `quality`：更长的 `TimeLimit` 和更严格的 `MIPGap`，用于追求更高解质量的实验。

### 4.4 测试项具体说明

1. `test_round2_default_values`

   该测试直接调用 `load_config()` 读取 `configs/default_sim.yaml`，并确认返回对象是 `ConfigBundle`。随后逐项检查仿真时隙长度、预测窗口、仿真总时长、两类核心数量、日照/阴影周期、能量上下界、初始电量、基础功耗、太阳能峰值功率、太阳能曲线、热模型参数和 Gurobi 默认参数。它验证的是第2轮写入 YAML 的关键实验默认值能够被配置模块准确解析并落到强类型配置对象上。

2. `test_missing_sections_fallback_to_reasonable_defaults`

   该测试在临时目录中创建一个只包含 `simulation.simulation_slots=180` 的 YAML 文件，然后调用 `load_config(...)`。测试检查显式配置的 `simulation_slots` 是否为 180，同时检查未写入的 `delta_t_seconds`、日照/阴影周期、Gurobi time limit、能量下限和太阳能峰值功率是否回退到默认值。它验证的是配置文件可以只覆盖少数字段，后续实验脚本不必重复写完整配置。

3. `test_missing_file_raises_clear_error`

   该测试把一个不存在的 YAML 路径传给 `load_config(...)`。预期配置模块抛出统一的 `ConfigError`，并在错误信息中包含 `Configuration file not found`。它验证的是配置路径错误能在加载阶段被清晰定位，而不是延迟到后续模块出现模糊错误。

4. `test_invalid_values_raise_clear_error`

   该测试创建一个非法 YAML，将 `delta_t_seconds` 设置为 `-1`。因为时隙长度必须为正，预期抛出 `ConfigError`，且错误信息明确指出 `delta_t_seconds must be > 0`。它验证的是配置模块不仅解析字段，还负责对关键字段做范围校验。

5. `test_core_count_config_supports_new_and_legacy_keys`

   该测试分两部分验证核心数量配置。第一部分使用新版字段 `high_performance_core_count=3` 和 `low_power_core_count=1`，预期总核心数为 4。第二部分只写旧字段 `core_count=5`，预期自动拆分为 2 个高性能核和 3 个低功耗核。它验证的是配置模块既支持当前异构核心设定，也兼容早期只配置总核心数的写法。

6. `test_tebs_modules_are_importable`

   该测试确认新增的 `tebs.config` 可以被自动导入，也确认 `__init__.py` 中导出的 `load_config`、`ConfigBundle` 等接口不会造成循环导入或导入阶段异常。

7. `tests/test_models.py` 全部测试

   第2轮全量回归会继续运行第1轮模型测试，用来确认新增配置依赖和包导出没有改变 `Task`、`TaskBlock`、`SystemState`、`ScheduleDecision` 等已有数据结构的行为。它验证的是第2轮改动没有破坏基础模型契约。
