```python
generate_task_set(

    num_tasks=None,
    random_seed=None,
    core_specs=None,

返回值为 `list[Task]`。每个 `Task` 内包含一个或多个 `TaskBlock`，每个任务块都带有：

- `deadline`
- `weight`
- `duration_by_core`
- `power_by_core`

### 3.3 7 类任务画像

本轮按实验方案落地 7 类任务：

| ID | 任务类型 | 负载特征 | 块数 | 权重 | 高功耗组 |
|---|---|---|---:|---:|---|
| T1 | 云检测 | 中等 AI 推理 | 4-8 | 2 | 否 |
| T2 | 云去除与压缩 | 多阶段中等负载 | 4 | 2 | 否 |
| T3 | SAR 船舶检测 | 高功耗、高产热、高时效 | 6-10 | 5 | 是 |
| T4 | 光学目标检测 | 中高 AI 推理 | 4-8 | 3 | 否 |
| T5 | 变化检测 | 高功耗、高时效、多阶段 | 4-6 | 5 | 是 |
| T6 | 图像压缩 | 低到中等负载 | 3-6 | 1 | 否 |
| T7 | SAR 后端处理 | 高功耗、多阶段 | 6-10 | 4 | 是 |

`T3/T5/T7` 被归入高功耗任务组，用于控制不同场景的热-电压力。

### 3.4 异构核心映射

任务工厂会为每个任务块生成覆盖全部核心的：

- `duration_by_core`
- `power_by_core`

当前规则：

- 高性能核：执行时间更短、功耗更高。
- 低功耗核：执行时间更长、功耗更低。
- 如果调用方没有传入 `core_specs`，则通过 `load_config()` 读取第2轮配置，再调用 `build_cores_from_type_counts(...)` 生成默认核心集合。
- 如果调用方传入自定义 `Core` 序列，则所有任务块只使用该自定义核心集合。

### 3.5 场景生成规则

`load_scenario_specs(...)` 会先加载内置场景，再把 `configs/scenarios.yaml` 中的字段合并到内置场景上。

当前支持：

- `S1_light`：轻负载，默认高功耗任务比例较低。
- `S2_mixed`：混合负载，默认 7 类任务均衡混合。
- `S3_stress`：高压力，默认提高 `T3/T5/T7` 占比。
- `S5_large`：大规模场景预留，用于后续 TCN 与大规模实验。

同时支持常用别名：

- `S1` / `light` -> `S1_light`
- `S2` / `mixed` -> `S2_mixed`
- `S3` / `stress` / `high_pressure` -> `S3_stress`
- `S5` / `large` -> `S5_large`

为了让场景压力稳定可测，`generate_task_set(...)` 不只按概率独立抽样，而是先根据 `high_power_task_ratio` 计算目标高功耗任务数量，再分别从高功耗组和非高功耗组中加权抽样。因此同样任务数量下，`S3_stress` 的高功耗任务数量会稳定高于 `S1_light`。

### 3.6 时间窗与前驱关系

每个生成任务满足：

- `Task.release_time <= Task.deadline`
- 所有任务块的 `release_time/deadline/weight` 与任务级字段一致。
- 每个任务至少包含一个任务块。
- 多块任务使用线性前驱链：`block 1` 依赖 `block 0`，`block 2` 依赖 `block 1`，依此类推。
- 每个任务块在所有可用核心上的执行时长均为正整数，功耗均为正数。

这种设计符合当前 `TaskBlock.predecessor_block_id` 的单前驱数据结构，也方便后续第8轮仿真器和第15轮 RHC-MILP 模型消费。

### 3.7 包导出

```

也可以：

### 4.4 测试项具体说明

1. `test_fixed_seed_generates_reproducible_task_set`

   该测试使用同样的场景 `S2_mixed`、同样的任务数量 `num_tasks=12` 和同样的 `random_seed=123` 连续生成两次任务集，并直接比较两个任务列表是否相等。它验证的是任务类型抽样、释放时间、截止期、块数、时长和功耗画像都受 seed 控制，可复现实验结果。

2. `test_stress_scenario_has_more_high_power_tasks_than_light_scenario`

   该测试分别在 `S1_light` 和 `S3_stress` 下生成 30 个任务，并统计高功耗任务数量和比例。由于 `S3_stress` 的 `high_power_task_ratio` 更高，预期其高功耗任务数量和比例均高于轻负载场景。它验证的是场景压力配置真实影响任务组成，后续实验才能用 S1/S3 对比热-电压力差异。

3. `test_generated_tasks_have_valid_blocks_and_positive_core_profiles`

   该测试在 `S2_mixed` 下生成 20 个任务，逐个检查任务是否包含任务块、任务时间窗是否合法、权重是否为正。对每个任务块，测试检查块级时间窗是否与任务级一致，`duration_by_core` 和 `power_by_core` 的核心集合是否一致且等于任务核心集合，所有执行时长和功耗是否为正。它验证的是任务工厂输出可以直接交给仿真器和 MILP 消费。

4. `test_multistage_predecessors_form_a_legal_chain`

   该测试使用场景别名 `mixed` 生成任务，并确认至少有一个多块任务。随后检查所有任务块的前驱关系：`block_id=0` 必须没有前驱，其余块的前驱必须正好是上一个块。它验证的是多阶段任务被构造成线性流水线，不会产生跳跃前驱、缺失前驱或环依赖。

5. `test_custom_core_specs_are_used_in_all_task_blocks`

   该测试构造两个自定义核心 `hp_custom` 和 `lp_custom`，然后调用 `generate_task_set("S1", ..., core_specs=cores)`。测试检查每个任务的 `core_ids` 是否等于自定义核心 ID，并检查每个任务块的时长/功耗映射是否只包含这两个核心。它验证的是任务工厂不固定依赖默认 2+2 核心布局，可以支持后续实验替换硬件核心配置。

6. `test_task_type_id_can_be_read_from_generated_task_id`

   该测试生成 1 个任务，并调用 `task_type_id_from_task(...)` 解析任务类型 ID。预期解析结果以 `T` 开头。它验证的是任务 ID 命名规则和任务类型解析函数一致，后续统计高功耗任务比例或按任务类型分组时可以可靠使用该接口。

7. `test_unknown_scenario_raises_clear_error`

   该测试传入不存在的场景名 `does_not_exist`。预期 `generate_task_set(...)` 抛出 `TaskFactoryError`，并在错误信息中列出未知场景问题。它验证的是场景名错误会在任务生成入口被清晰拦截，而不是生成一个隐式默认场景导致实验配置错误。

8. `test_tebs_modules_are_importable`

   该测试确认 `task_factory.py` 可以被自动导入。第3轮首次运行时曾发现 `TaskTypeSpec` 常量初始化早于校验函数定义导致 `NameError`，该导入测试正是用来捕获这类模块初始化顺序问题。修复后，任务工厂导入无异常。

9. `tests/test_models.py` 与 `tests/test_config.py`

   第3轮全量回归会继续运行第1轮模型测试和第2轮配置测试。这样可以确认任务工厂复用 `Task`、`TaskBlock`、`Core`、`ConfigBundle` 时，没有修改或破坏已有数据契约和配置加载行为。

## 5. 与后续轮次衔接

当前任务工厂已经可以直接支撑：

- 第4轮 `environment.py`：使用任务释放时间与场景仿真长度生成轨道环境。
