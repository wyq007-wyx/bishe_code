### 3.2 `baseline_fcfs_gurobi.py` 实现内容

新增主要对象与接口：

- `GurobiWindowAssignment`：记录窗口计划中的时隙、核心、任务块、执行时长和计算功耗。
- `FcfsGurobiScheduler`：固定 FCFS 队列的 Gurobi 强基线。
- `FcfsGurobiError`：Gurobi 不可用或求解失败且禁用 fallback 时的清晰错误。

调度策略：

```text
1. 任务按 (release_time, task_id) 固定排序。
2. 若队首任务未释放，则所有核心 idle，不允许跳过队首。
3. 若队首任务块前驱未完成，则所有核心 idle。
4. 对当前队首 ready block 建立小 MILP。
5. Gurobi 在兼容核心中选择一个核心执行当前时隙。
6. MILP 约束当前能量下限和热预算。
7. 返回当前时隙动作，并把求解状态写入 SolverTrace。
```

当前 MILP 约束：

```text
sum_c x_c = 1
compute_power * Delta t <= available_energy
compute_power * Delta t <= thermal_budget
x_c in {0, 1}
```

目标函数：

```text
min duration_on_core + 0.001 * power_on_core
```

该目标使强基线只体现异构核心匹配能力，不获得任务重排能力。

### 3.3 无 Gurobi 环境行为

模块导入不依赖 Gurobi。调度器默认 `fallback_to_idle_on_error=True`，当 `gurobipy` 不存在或 license 不可用时，会返回安全 idle 并记录 `GUROBI_UNAVAILABLE` 或 `UNKNOWN` 状态。测试中真正求解的用例会在无 Gurobi 时自动 skip。

### 4.4 测试项具体说明

1. `test_fcfs_gurobi_does_not_skip_queue_head_when_unreleased`

   该测试构造两个任务：队首 `T0` 在时隙 2 才释放，后续任务 `T1` 在时隙 0 已释放。当前时隙为 0。预期调度器返回所有核心 idle，而不是跳过 `T0` 去执行 `T1`。它验证的是 FCFS-Gurobi 强基线固定任务顺序，不具备主方法的任务重排能力。

2. `test_fcfs_gurobi_solves_toy_case_and_keeps_fcfs_order`

   该测试构造两个都已释放的单块任务和两个异构核心。Gurobi 只允许对队首 `T0` 的当前块选择核心，预期返回一个非 idle 决策，且 `task_id` 必须是 `T0`。测试还检查 `solver_trace.has_feasible_solution=True` 和 `last_window_plan` 已记录计划。当前环境没有可用 Gurobi，因此该求解型测试自动 skip。

3. `test_tebs_modules_are_importable`

   该测试确认 `baseline_fcfs_gurobi.py` 能在没有 Gurobi 的环境中导入，且 `__init__.py` 的新增导出不会导致导入阶段错误。
